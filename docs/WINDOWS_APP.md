# The Windows program

1.3.0 turns the project into something you install, not something you unpack and start
with a batch file. This page is for whoever maintains that build.

**Arabic, step by step, for the person using it:** [INSTALL_WINDOWS_AR.md](INSTALL_WINDOWS_AR.md).

## What ships

| File | What it is |
|---|---|
| `ACQ-Setup-<version>.exe` | The installer. Double-click, Next, Install, Finish. Per user, no administrator prompt. |
| `ACQ.exe` | The program. Windowed, no console, no Python on the machine. |
| `desktop/acq.ico` | The icon, generated by `scripts/make_icon.py` (no image library). |
| `desktop/acq_app.py` | The entry point: instance lock → credentials → server thread → window. |
| `desktop/acq.spec` | PyInstaller definition: what is bundled and what is excluded. |
| `desktop/installer.iss` | Inno Setup definition: shortcuts, startup option, uninstall rule. |
| `scripts/build_windows.py` | One command that builds both files. |
| `.github/workflows/windows-app.yml` | The same build on a free GitHub Windows runner. |

## Two folders, on purpose

| | Where | Replaced by an update? |
|---|---|---|
| Program files (interface, migrations, fixtures, `ACQ.exe`) | `%LOCALAPPDATA%\Programs\AcquisitionsAssistant` | yes, wholesale |
| Your files (`data\acquisitions.db`, `.env`, `data\backups`) | `%LOCALAPPDATA%\AcquisitionsAssistant` | **never** |

`app/paths.py` is the only place that decides this. `runtime_root()` is the read-only bundle
(PyInstaller's `sys._MEIPASS`), `data_root()` is the person's folder. Running from source both
resolve to the repository, which is why every existing script and test still works, and why an
old ZIP folder opens with the database it already has.

`adopt_legacy_data()` covers the only dangerous upgrade path: an installed 1.3.0 opening next to
a 1.2.x folder that holds the real database. It copies the database and `.env` across once, leaves
the originals untouched, and writes `.adopted-from-program-folder` so it never runs twice.

## Window behaviour

1. `ACQ.exe` starts with **no console**.
2. A lock file (`acq.lock`, a real OS file lock) guarantees one copy. A second launch opens the
   running one instead of starting a second server on the same database.
3. The server runs on a background thread with uvicorn's signal handling disabled (it would
   otherwise install handlers that only belong to a console process).
4. The window is a WebView2 window (pywebview) when the runtime exists, otherwise a small Tk
   control window showing the address, the phone address and the password, otherwise the default
   browser. Each fallback is a deliberate degradation, not an accident.
5. Closing the window stops the server and releases the lock.

## Building

Free, either way.

**On GitHub (no local tooling):**

```
git tag v1.3.0 && git push origin v1.3.0
```

The `Windows app` workflow builds, smoke-tests and attaches `ACQ.exe` and `ACQ-Setup-*.exe` to the
release. What the smoke test proves before anything is published:

- `/api/health` answers from the packaged executable;
- `/` serves the compiled interface from inside it;
- a database and a password file appear in the data folder — not inside the bundle;
- a second copy exits without starting a second server.

**On your own Windows machine:**

```
python scripts/build_windows.py
```

Requires Python 3.11, Node.js and [Inno Setup](https://jrsoftware.org/isdl.php). Produces
`dist\ACQ.exe` and `dist\ACQ-Setup-<version>.exe`.

## Proving the layout without PyInstaller

`scripts/test_frozen_layout.py` builds the same bundle layout in a temporary folder, fakes the
three attributes PyInstaller sets (`sys.frozen`, `sys._MEIPASS`, `sys.executable`) and boots the
real app from inside it. It asserts the interface is served, the migrations apply to a database in
the data folder, the revision is `0a6d91cf17b2`, and no file escaped into the bundle. CI runs it on
every push, so a file the spec forgets to carry fails there instead of on a user's PC.

## Proving the program behaves like an installed program

`scripts/smoke_desktop_app.py` starts `desktop/acq_app.py` twice as a real process, with a
temporary data folder, and checks the whole lifecycle:

1. first start: `/api/health` answers, `/` serves the interface, the password appears in
   `<data folder>\.env`, the database appears in `<data folder>\data`, and nothing lands in the
   program folder;
2. a second copy with the same folder exits 0 and never opens a port;
3. one seller is imported through the real upload → preview → approve endpoints;
4. the program is stopped and started again: the saved password still works and the seller is
   still listed.

Both CI and the Windows workflow run it before building, so a change that breaks the data folder
or the restart path fails in the checks instead of on your PC.

## Code signing

Not signed. A certificate costs money every year and the project is meant to be free, so the first
run of a downloaded installer shows **Windows protected your PC → More info → Run anyway** once.
That prompt cannot be removed in code; it is the honest trade-off, and it is stated in the Arabic
guide and in the release notes.

## Not verified here

- No Windows machine and no display in this development environment: `ACQ.exe` itself, the WebView2
  window, the Tk fallback and the Inno Setup installer are exercised only by the GitHub Windows
  runner and by you. Everything that can be checked without Windows — the folder split, the
  adoption of an old database, the instance lock, the window logic with a stub webview, the frozen
  layout, the version and icon generation — is covered by tests.
